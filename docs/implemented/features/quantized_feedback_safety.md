# 量化反馈判定与同步审计

本页描述已实现的软件策略与离线证据；当前版本尚未做真机验收。项目状态以
[project_status.md](../../reference/project_status.md) 为准。控制器负责设备与保持，
运动层拥有轨迹导数和跟踪检查；没有新建 SDK 或更换 MotorBridge 安装版本。

## 运行期判定

`pose_compat_node` 显式使用 `TrajectoryRuntimeLimitGuard(derivative_policy='diagnostic')`。
反馈速度的差分加速度和 jerk 保留为诊断，不能单独触发中止。直接速度、力矩
上界、0.20 rad 跟踪误差、150 ms 新鲜度、连续性代次及设备错误检查仍生效。
其他调用者默认仍为 `enforce`；规划和重定时继续执行 YAML 的速度、加速度与
jerk 限位，`max_jerk=20` 未改。没有增加未经验证的滤波器。

期望位置按反馈 ROS 源时间减去轨迹派发 ROS 时间采样，避免用回调到达时刻
比较旧反馈。派发时刻仍不等于电机开始响应的时刻，需结合实际发送审计验证。

| 用途 | 连续窗口 | 保留的速度门限 | 位置条件 |
| --- | --- | --- | --- |
| ArmStop | 0.20 s | 0.05 rad/s | 六轴全极差及固定保持锚点位移均 ≤ 3 编码 |
| motion 停止确认 | 0.30 s | 0.03 rad/s | 六轴全极差及请求首帧锚点位移均 ≤ 3 编码 |
| 现场失能过渡诊断 | 失能状态后 1 s | 0.07 rad/s | 七路原始电机全极差及整个过渡锚点位移均 ≤ 3 编码 |

位置编码取 `25/65535 rad`，三个编码约 `0.00114443 rad`。这些是待真机验证的
软件策略，不能理解为物理无运动保证；小于编码及窗口分辨率的运动无法排除。
0.20/0.30/1 s 提供多个独立样本，也会增加确认时间。全极差拒绝同端点振荡，
固定锚点防止滑窗跟随累积漂移。

窗口至少三个独立源样本，相邻间隔不超过 150 ms。控制器还要求各轴序号均推进。
重复缓存不累计时间；无效值、源时间/序号倒退和断流不能确认停止。motion 的
空档/状态变化使跨空档旧请求失效；恢复后的新帧不能抹掉空档，新请求可重建证据。
新显式停止可等健康流到达后开始观察；已经开始的窗口断流则保留失败。位姿取消
在取得动作终态后另建保持确认，反馈代次变化和原执行错误仍保留，不能恢复成成功。
单帧速度超限会记录并延迟确认，必须等之后完整的正常窗口；持续超限始终阻断。
没有把超限判为必然噪声，没有放宽速度门限或设置失能后的速度盲区。

## 保持与失能边界

只有 POS_VEL 正常循环、无活动轨迹/重力/透传、已有静止证据且旧目标接近反馈时，
停止才保留旧目标。仍递增执行及请求代次，使旧命令失效。运动取消重新取反馈保持。
孤立速度峰使新静止窗口失效时，150 ms 内的既有保持确认可用于保留近处原目标，
不能用于停止成功应答；位移、断流和目标代次改变立即使该历史确认失效。
`ensure_pos_vel_control` 不再在已运行的位置循环中隐式重设目标。重复停止请求
加入同一确认，不重设目标；设备会话变更仍能取消等待及迟到续体。
控制器停止总预算仍为 2 s，健康超时保持使能，设备故障仍走保护路径。

`DisabledTransitionEvidence` 是纯诊断器，不改变生产 `disable` 事务或主动发命令。
它要求服务成功回执、请求后七路新鲜失能状态、整个过渡位移界及之后一秒静止。
孤立速度峰记录并延迟确认；空档、未知状态及位移超界锁存失败，后续恢复不能改写。
输入均为七路原始电机 rad/rad/s，不能把夹爪开口 m 当成电机角度。实机使用仍须
现场授权及失能前基线检查。没有修改 `pos_ki`，J6 积分/粘滑解释仍待验证。

## 审计入口

[audit_feedback_session.py](../../../scripts/audit_feedback_session.py) 配置标准库
`rebotarm.audit` 日志并运行既有节点 `main(args)`。生产者有界非阻塞入队，审计
线程做 JSON 编码及写盘。节点使用相同会话名、不同输出文件；记录 PID、单调/
墙钟时间、源码 SHA256、MotorBridge 版本及以下信息：

- MotorPort 读到的新序号、数值和状态；验证缓存的序号及真实观测时间；
- ROS 源时间与六轴序号元组的映射；
- 实际位置命令、速度限制、目标代次和成功/部分失败回执；
- 停止前后目标、是否保留旧目标及确认所用序号；
- 位姿守卫实际消费的源时间、速度/力矩、期望位置、误差和差分诊断。

SDK 缓存观测可能跳过中间帧，不能称为原始接收帧。可选 `--serial` 独占真实
串口并转发到 PTY；此入口只支持 MotorBridge 的 DM 串口协议。记录原始双向
字节块；MotorBridge 仅打开该 PTY。TX 按 `55 aa 1e 03` 和固定 30 字节缓存
半帧、拆开粘包，载荷原样逐帧写入并排空发送缓冲，帧间至少 120 μs（与 SDK
默认多电机间隔相同）。未知帧头、部分写入、关闭时未转发的字节均使审计无效；
不自动补发。RX 保留原始分段/粘包，不解码或改写反馈。

`raw_serial` 的 `read_ns` 是代理实际读取时刻；`relay_forward` 另记每次转发
的 `read_ns/started_ns/completed_ns` 及原样字节，`relay_closed` 记录关闭错误。
完成时间只表示主机写入/排空返回，不是 USB 到达时间或电机 CAN 应答。字节块
需按帧头、ID、长度、顺序离线解析并与序号核对，不承诺天然一一对应。
代理会引入调度开销，实际 USB 分包与延迟必须在下次实机审计测量。

未授权时只运行离线回放及虚拟 PTY 测试。以下仅供之后获授权的会话参考：

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash
# 先按 AGENTS.md 完成现场检查、通道占用检查和本轮明确授权。
python3 scripts/audit_feedback_session.py --session SESSION --output CONTROLLER.jsonl \
  --module rebotarmcontroller.rebotarm_controller --serial /dev/ttyACM0 --baud 921600 \
  -- --ros-args -p 'channel:={audit_serial}'
python3 scripts/audit_feedback_session.py --session SESSION --output MOTION.jsonl \
  --module rebotarm_motion.pose_compat_node -- --ros-args
```

输出独占创建，避免覆盖。结束摘要包含 accepted/written/dropped/errors；丢弃、
编码/写盘失败、代理/清理错误、缺少结束摘要均表示证据不完整，不能据此验收。
节点构造失败或代理清理抛错时也尝试排空审计线程；计数完整只说明日志写完，
不能覆盖会话失败或未发送的命令。退出后仍须检查进程、串口占用和设备状态。
审计线程不能替代设备保护或急停；控制器和运动日志都必须齐备。

### 2026-10-29 启动失败的离线排查

两轮失败记录位于 `log/hardware_feedback_20261029_session/` 和
`log/hardware_feedback_20261029_retest/`。在首条失能 TX 之前，按连续字节流
解析均有三批、每批七条反馈请求，所有 TX 帧头和顺序完整；没有使能或运动命令。

| 会话 | 代理 TX 读取块（30/60/90 字节） | 清理前反馈 ID | 三次轮询时刻（会话起点起，ms） |
| --- | --- | --- | --- |
| session | 7 / 4 / 2 次 | 0x11、0x14、0x17、0x13、0x14、0x15 | 72.30 / 124.05 / 175.87 |
| retest | 5 / 5 / 2 次 | 0x11、0x11、0x14、0x11、0x17 | 69.11 / 120.57 / 172.38 |

旧代理按读取块直接 `serial.write`，将 SDK 的多次 30 字节写入合并；前两批
合并块与缺失应答相关，但旧日志没有转发完成时刻、USB 抓包或直连同条件对照，
尚不能证明适配器如何处理这些写入。两轮 69 字节 ASCII 菜单均在失能清理开始
之后出现，不能据此解释之前的启动失败，来源仍未确定。MotorBridge 使用会
释放 GIL 的 `ctypes.CDLL`，没有证据支持“SDK 持有 GIL 阻塞代理”的归因。

独立复现了启动刷新提前结束：三轮约在 0/50/100 ms 请求并立即非阻塞轮询，
第三轮之后没有等待。虚拟时钟下 110 ms 才到的一路应答处于既有 150 ms 响应
窗口内，旧实现仍失败。修复只在原窗口剩余时间内每约 5 ms 轮询，不再发新请求
或重建截止时间；第三轮后的额外等待最多 50 ms，缺路、窗口外应答、调度超时
和总线异常仍失败。150 ms 新鲜度与逐电机序号规则均保留。

虚拟串口验证了分段重组、逐帧写入间隔、关闭残留和异常清理；已安装的真实 SDK
在直连/代理两种虚拟链路均能取得七路独立序号。离线证据在
`log/audit_startup_20261029/`。这不证明 USB 适配器的实机回包问题已经解决。
下一轮现场授权后，先保持失能做直连/代理同请求节拍对照、核对写入完成和逐路
回包；启动与连续新鲜反馈稳定后，再恢复此前夹爪 5 mm 往返范围，先不测 J1。

## 夹爪回归的监测与动作交接

2026-10-29 的临时回归使用两个独立客户端：旧客户端在夹爪运动时仍按静止门限
锁存速度异常并请求六轴停止，恢复客户端却不知道该锁存，继续发送了返程目标。
旧临时脚本及其日志只作为历史证据，不再作为后续验收工具。

`scripts/hardware_regression.py` 将夹爪回归的监测、故障锁存和目标发送放在同一
进程；同一用户的同机实例使用文件锁互斥，同一 ROS 域内还检查旧监测节点。它不是全局 ROS
访问控制，无法阻止其他域、其他用户或不使用此协议的客户端，现场仍须自行核对
并停止其他命令和监测进程。启动仅接受新鲜的默认失能状态，命令必须显式输入，
不会自动使能或运动。故障不可在本轮内重置；后续使能和夹爪目标被拒绝。故障时
请求六轴停止保持，并取消已接纳的夹爪目标；目标在故障后才接纳时仍取消。取消
请求、取消回执和动作终态分别记录，回执本身不等于停止确认。未知接纳或未被
调用方取得的迟到终态继续阻断本工具收尾；本工具没有接管已使能设备的恢复客户端。

同一所有者在夹爪目标待接纳或运行时使用控制器的夹爪速度上限，其他时候使用
原 0.07 rad/s 静止门限；六轴门限不变，均按不同源帧累计。切换阶段清空速度
累计，不改写源时间或跳过反馈新鲜度、位置范围、状态和审计检查。监测检查异常
或超过 150 ms 未完成检查时锁存并请求停止保持；监测调用本身卡住也不阻塞停止
请求或已知夹爪目标的取消。客户端审计采用有界队列，丢弃或写入错误使会话失效。现场失能仍须显式
命令、已验证基线和一秒七路静止，过渡检查继续保留异常和断流证据。

七路反馈和状态订阅使用专用节点及单线程执行器；Service、Action 与节点图查询
使用另一个节点及执行器。两者仍在同一 Python 进程，不能保证完全消除调度干扰。
任一执行器异常退出使监测锁存；监测故障的首次单调时间、停止请求的开始和返回、
取消调用的开始及后续回执分开记录，无法取得回执时不得当作已停止。停止请求和
夹爪取消并行发起，任一发送入口卡住不能拖住另一请求；迟到接纳仍执行取消。
原 150 ms 新鲜度、周期性旧监测者查询与故障锁存规则不变。
故障和请求起始记录由独立队列转交审计线程，按 `at_mono` 和 `fault_mono` 判断
实际先后，文件落盘顺序可能不同；审计卡住不能阻塞停止或取消发送。
发送入口等待时不占用故障锁，故障时已经准入的请求仍可能在途；夹爪目标迟到
接纳后必须取消。使能请求若此时状态未知，不能假定它未送达，也不能重试或自动失能，
须根据新鲜反馈和回执处理现场。
停止调用尚未返回、取消发送线程尚未退出或取消回执未完成时，工具不允许正常退出；
动作终态不能替代这些在途操作的确认。

上次 20 mm 现场回归的客户端把订阅、Service 和 Action 放在同一单线程执行器；
离线人为阻塞 Service 回调可在该客户端诱发反馈空档，但上次现场空档发生在动作前，
现有日志不能证明它由同一原因导致。周期性节点图查询在两组各约 25 s 的隔离对照中
均未复现过期，也不能证明现场空档与之无关。该限制不应作为网页遥操作或电机故障结论。

工具需要调用者先完成本轮现场授权、串口独占检查、只读预检和控制器启动，准备
当次 `baseline.json` 和实时 `controller_audit.jsonl`；接着用新的会话目录执行
`python3 scripts/hardware_regression.py <会话目录>`，按 `disabled10`、`enable_hold`、
`gripper_roundtrip` 的顺序逐项输入，夹爪动作前会按当前姿态重新做 21 点碰撞检查。
结束需显式 `disable` 与 `quit`，并独立检查控制器审计摘要和串口释放。此工具不能
替代现场急停、控制器保护、授权或独立审计；若输入中断、目标终态不明或监测失败，
不得通过另起恢复客户端继续运动。反馈执行器隔离和停止交接调整仅经离线模拟，
尚未用于新一轮真机。

## 回放与证据限制

```bash
python3 scripts/replay_feedback_policy.py \
  log/controller_consumer_hardware_20261028_222427 log/jerk_retest_20261028 \
  log/gripper_roundtrip_20261028 --output /tmp/feedback_policy_replay.json
```

工具记录输入 SHA256，按六轴序号元组去重；不重写旧日志或历史验收。旧日志缺
每周期目标和守卫实际输入，回放只是策略敏感性比较。夹爪会话 J6 约 0.005341 rad
偏移超过锚点范围，新策略仍拒绝它。

历史三点 J1 速度 `0.00244236 → 0.01220989 → 0.00244236 rad/s`、约 24.32/
23.63 ms 间隔按生产浮点时间差分重现 `−34.4837183 rad/s³`，对应两编码脉冲。
一个编码在 20 ms 也足以超过 20，不能把历史报告写成 23.6 ms 下的单编码跳变。
独立缓存重现数值仍不能证明原守卫恰好消费了这三个点。

反例覆盖持续运动、慢漂移、同端点振荡、持续速度越限、重复缓存、空档恢复、
非有限值、独立序号及失能回执/状态缺失；实际位姿监控测试验证源时间对齐和审计。
PTY 测试只验证软件转发。全部软件结果都不能替代当前版本的真机验收。
