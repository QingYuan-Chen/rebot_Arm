# docs 维护原则

> 状态：REFERENCE；类型：文档治理规则；适用范围：`docs/` 全部 Markdown 文档。

本文档定义 `docs/` 的分类、状态和更新规则，避免把设计、当前实现和历史报告混在一起。

## 文档状态

每份重要文档顶部应标注一种状态：

- `IMPLEMENTED`：当前代码中已有，并有软件或仿真验证的功能。
- `SETUP`：clone、依赖、环境和构建说明。
- `DESIGN`：当前仍在讨论或实施中的技术方案。
- `REFERENCE`：参数、接口、拓扑或术语参考，不单独表示功能已验收。
- `USER-MAINTAINED`：用户本人维护，代理不得擅自修改。

建议同时写明：适用范围、最后核对日期、验证依据和硬件边界。

## 统一文档格式

除用户维护清单外，文档顶部统一使用以下顺序：

```markdown
# 文档标题

> 状态：<IMPLEMENTED|SETUP|DESIGN|REFERENCE|USER-MAINTAINED>；类型：<文档类型>；适用范围：<范围>。

## 当前范围

用一段话说明本文解决什么问题，以及不包含什么。
```

专题文档随后按“当前范围 → 前置条件/依赖 → 操作或设计内容 → 验证结果 → 边界与限制 → 相关文档”的顺序组织。命令文档必须把可复制命令放在 fenced code block 中，并在命令前说明执行目录、环境和安全前提；参数、节点、数据流参考应优先使用表格或 Mermaid/ASCII 图，不要在多个文件重复维护同一组默认值。

状态只使用上面五个枚举值；`CURRENT`、`REFERENCE` 混用或仅写“已完成”都不再作为新文档格式。`REFERENCE` 表示查阅资料，不表示功能已验收；`IMPLEMENTED` 也必须说明软件、仿真和真机边界。

## 生命周期

```text
设计方案 -> 用户决策 -> 实现 -> 测试/验收 -> IMPLEMENTED as-built
                              └-> 未采用/已替换 -> Git history
```

- 技术路线完成后，把已采用部分转化为当前架构/操作契约；未采用或已替换方案从工作树移除，需要追溯时使用 Git history。
- 架构边界不能因为实现完成而删除；它是后续代码归属和依赖审查的长期约束。
- 差异报告和迁移清单是时间快照，必须标明日期，不得当作当前源码清单。
- 使用文档只保留当前可执行命令；删除的入口只在历史迁移文档中说明。
- 验收文档必须区分“通过”“未通过”“范围关闭”和“未实测”，不能用范围关闭冒充通过。

## 更新规则

1. 先核对当前代码、测试和用户最新决定，再修改文档。
2. 修改 launch、参数、包边界或操作命令时，同步更新对应 `implemented/`、`reference/` 或 `setup/` 文档和 `docs/README_zh.md` 索引。
3. 仅软件验证不得写成真实硬件验收；硬件动作必须记录授权和现场边界。
4. 废弃路线从当前索引移出并从工作树删除，需要追溯时使用 Git history，不作为当前入口。
5. 不重复复制同一份参数；选择一个权威来源，其余文档链接到它。
6. 文档修改后至少执行 `git diff --check`，涉及命令时核对命令是否仍存在。
7. `user/USER_MAINTAINED_TODO.md` 只能由用户明确要求时修改、移动、重命名或删除。

## 当前目录结构

实体文档按职责放入 `implemented/`、`setup/`、`design/`、`reference/` 和 `user/`；根目录只保留总索引和维护规则。历史资料不建立独立目录，统一从 Git history 追溯。新增文档必须先选择唯一权威目录，不能为了方便复制到多个目录。
