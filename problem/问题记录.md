## P001：为什么硬件反馈采集完成后不直接发布关节状态？

记录日期：2026-10-22。

处理状态：仅记录，尚未批准修改；未实施修复。

### 用户发现的问题

在 `interactive_system.launch.py` 中同时存在：

```python
DeclareLaunchArgument("joint_state_rate", default_value="100.0"),
DeclareLaunchArgument("hardware_feedback_rate_hz", default_value="50.0"),
```

用户提出：

> 为什么既有关节状态又有硬件反馈，这说的不是同一个东西吗？
>
> 为什么不采集完就发布？

### 当前源码行为

- `hardware_feedback_rate_hz` 控制共享总线反馈批次的刷新频率上限，默认 50 Hz；实际频率受调度和通信耗时等因素影响。
- `joint_state_rate` 控制 ROS 状态发布定时器的目标频率，默认 100 Hz；发布器读取最近的已校验反馈缓存。
- 硬件控制循环运行时，由该循环发起反馈事务，ROS 发布侧读取缓存；没有硬件控制循环时，发布回调会尝试触发到期的限速刷新，因此两者并非在所有状态下完全独立。
- 同一批反馈可能被多次发布。当前实现会按反馈接收序号识别批次，重复批次沿用原时间戳，不会因重复发布而获得新的采样时间。

正常、稳定运行的理想情况下，50 Hz 采集、100 Hz 发布可能表现为同一批反馈发布两次，并不代表每秒获得 100 份新的硬件反馈。

### 需要讨论的问题

1. 对这条真机关节状态链路，独立设置发布频率的实际需求是什么？是否需要重复发布同一批反馈？
2. 定时读取缓存可能增加从新反馈可用到消息发布的等待；是否应改为新反馈到达后通知 ROS 发布？当前尚未实测这一等待的大小及其影响。
3. 部分注释将提高关节状态发布频率描述为“越高越实时，同时总线负载越大”，容易混淆消息发布频率与硬件采集频率。控制循环运行时，提高发布频率主要增加 ROS 消息和 CPU 开销，不会直接提高硬件采样频率；没有控制循环时还需结合发布回调触发刷新的行为分析。

### 待用户批准后评估的方向

可考虑事件驱动：硬件采集完成后更新缓存并发出通知，由 ROS 执行器处理发布，避免把消息构造和发布直接放入硬件控制线程。处理不及时时只保留最新反馈，避免排队积压。

这只是候选方案，尚未决定采用。实施前需讨论通知机制、消息频率要求、反馈时间戳、故障状态发布及对 MoveIt、可视化订阅端的影响。

### 源码依据与验证范围

- [启动参数](../src/rebotarm_bringup/launch/interactive_system.launch.py)：两个频率参数的默认值及注释。
- [控制器装配](../src/rebotarmcontroller/rebotarmcontroller/rebotarm_controller.py)：分别向硬件管理器与 ROS 发布器传入频率参数。
- [ROS 状态发布器](../src/rebotarmcontroller/rebotarmcontroller/ros/ros_publishers.py)：定时发布、缓存读取、反馈批次识别与重复批次时间戳保留。
- [硬件管理器](../src/rebotarmcontroller/rebotarmcontroller/hardware_manager.py)：`refresh_feedback_if_due()` 的反馈限速与总线访问控制。

以上结论来自源码阅读。本次仅建立问题记录，没有修改实现、调整参数、运行实机或测量运行时延迟。

## P003：网页只读监视依赖硬件控制节点，连接过程可能改变电机状态

记录日期：2026-10-25。

处理状态：严格只读模式待讨论和批准，尚未实施或验收。

### 用户发现的问题

用户希望不启动运动控制链路，只在网页查看真实关节状态，并提出：

> 如果我不启动控制链路，只是想在网页读取一下关节状态也会被这个255状态码给卡住的吧

需要明确区分“启动硬件通信并读取反馈”“使能电机”和“执行运动”。只查看状态不应被理解为同意改变电机的使能状态、模式或运动目标。

### 当前源码行为

- 真实反馈路径为：电机 → `rebotarmcontroller` 采集并发布 ROS 话题 → Dashboard 订阅并存储 → HTTP/SSE → 网页。网页本身不访问电机 SDK；只有网页而没有真实反馈发布者时，无法得到实时关节状态。
- 当前硬件节点同时持有反馈采集、状态发布和运动控制接口。节点连接成功后，即使保持失能、没有运行运动控制循环，ROS 发布定时器仍会调用 `refresh_feedback_if_due()`，按配置频率刷新并发布反馈。因此，读取反馈不要求先使能，也不要求启动 MoveIt 或执行抓取。
- 节点构造时自动调用 `HardwareManager.connect()`。连接流程读取机械臂和夹爪状态；若发现任一电机状态非失能值 `0`，会调用 `_disable_all_motors()`，再验证状态。连接异常清理和正常关闭路径也会尝试失能。因此，“启动现有硬件节点但不点击使能”不等于“严格只读、不改变设备状态”。
- 若连接阶段失败，控制节点会退出，后续状态发布器和服务不会正常装配，网页也就缺少该节点提供的实时数据。不能把这种情况一概归因于 `255`。

### `255` 的含义与问题边界

- `255` 由控制器统一缓存可用性判定产生，表示缺少可信反馈；不是写入电机的命令、电机故障码或硬件锁。
- 动作入口另行检查连接、使能、反馈有效性与时效，以及相应控制循环条件。
- `get_gripper_state()` 在反馈缺失、过期、读取异常或坐标非法时，也会对外返回 `255`。未采集、采集失败和电机自身报告故障应分别解释，不能只凭 `255` 判断电机损坏。
- 网页关节表直接显示位置、速度、力矩和状态码，没有因为 `status_code == 255` 而整体拒绝显示。真实反馈采集不可用才是没有实时数据的原因；修改初值不能建立缺失的通信链路。

### 待用户批准后评估的方向

1. 评估独立的只读接入模式：允许连接、查询反馈和发布状态，但启动、运行、异常处理及退出都不得隐式使能、失能、切换模式、置零或发送运动目标。反馈查询所需的协议请求属于采集，需与改变设备状态的命令区分。
2. 采集和硬件连接仍归 `rebotarmcontroller`；Dashboard 继续订阅状态，不直接引入 SDK。只读与控制模式须共用或明确交接唯一的总线所有者，不能为网页另开第二个驱动会话。
3. 界面区分未连接、等待首帧、反馈过期、读取失败、电机故障与正常失能；保留反馈时间信息，不把旧数值当作当前状态。仅查看状态的界面不应以使能为前提。
4. 后续验收应分别覆盖只读启动、无反馈、掉线恢复、状态发布与退出，并检查实际 SDK 调用是否包含改变设备状态的命令。软件测试不能替代真机只读行为验收。

以上仅为讨论方向，尚未选定实现方案；不得直接删除现有控制模式的安全检查或失能处理来实现只读需求。

### 源码依据与验证范围

- [控制节点装配](../src/rebotarmcontroller/rebotarmcontroller/rebotarm_controller.py)：先 `connect()`，成功后创建状态发布器及控制接口。
- [硬件管理器](../src/rebotarmcontroller/rebotarmcontroller/hardware_manager.py)：初始状态、反馈更新、`connect()`、连接失败清理及 `shutdown()`。
- [ROS 状态发布器](../src/rebotarmcontroller/rebotarmcontroller/ros/ros_publishers.py)：失能时的反馈刷新与话题发布。
- [Dashboard 节点](../src/rebotarm_dashboard/rebotarm_dashboard/teleop_status_panel_node.py)：关节、电机和夹爪状态订阅及存储更新。
- [网页关节表](../src/rebotarm_dashboard/rebotarm_dashboard/status_panel_assets/index.html)：`updateMotorRows()` 直接显示数值与状态码。

本条来自源码核对，严格只读模式仍待讨论与验收；未以网页查询为由连接、使能、失能或操作真实电机。

## P004：夹指未随夹爪左右关节运动

## P005：真机轨迹执行未在相邻点之间按时间插值

记录日期：2026-10-29。

处理状态：2026-11-04 已撤销七轴 FJT，改为完整六轴轨迹与独立夹爪。网页 prepared_v1 由 ExecuteTeleopMotion 同周期登记两侧、分别推进并汇总终态；碰撞计算副本固定闭合双指，其他入口固定新鲜真实开度。MoveIt 只保留 arm/gripper 独立执行，示教恢复六轴、视觉先预张爪完成再规划。最终计划已在重定时前绑定保持起点，准备不再修改该曲线；原超限拒绝保留，约 0.001144 rad 门限及静止准入窗口不恢复。完整回归、独立构建、假设备 ROS 与 MuJoCo 链验证见本轮功能记录。先前现场首次任务失败原因仍缺原始证据；实机仍 legacy、默认失能，日常仿真 prepared_v1，用户实测、默认切换及实机定量验收未完成。

示教修订：q/v 录制按三次 C1 回放，不补算 a 升级 C2；示教专用 MoveIt 对齐显式转换
同等级后，完整曲线重新限值和碰撞检查。v5 保存导数来源且不覆盖原始/旧派生文件。
309 点记录的软件、独立安装区及 MuJoCo 对齐/取消/再次回放结果见
[示教 C1 验收](../docs/implemented/features/teach_replay.md#c1-修订验收2026-11-04)。普通 MoveIt 执行不转换，实机结论不变。

### 问题与当前行为

用户在 RViz 规划真机执行时观察到轻微抖动，并关注轨迹点间插值以及速度、加速度是否连续。

当前真机 FJT 执行器只接收轨迹点的位置和时间，在下一个点到期前保持上一位置目标；若同一控制周期内多个点到期，只取最新目标。控制器没有在相邻点之间按时间生成线性插值目标，也没有使用轨迹点中的速度和加速度重建连续轨迹。控制循环配置的 500 Hz 为名义周期，并非轨迹点频率或实际发送时间保证。

这一限制属于真机六轴 FJT 共用执行层，并非 MoveIt 专有。网页关节点对点执行先用三次 smoothstep 曲线生成位置点，期望采样间隔为 50 ms，再通过同一 FJT 下发；控制器仍在这些点之间保持上一目标。网页键盘单步的直接 FJT 路径每次只发送一个带目标时间的位置点，也不会在起点与目标之间生成连续参考。网页夹爪使用独立执行路径，不直接归入本问题。

用户此前反馈网页遥操作实机测试未发现问题；这与代码中存在点间目标保持并不矛盾。实际运动是否平稳取决于轨迹点密度、发送时序、电机固件及机械响应，目前不能仅凭代码确认实机速度、加速度的连续性或认定抖动原因。

MoveIt 配置了 TOTG 时间参数化和 Ruckig 平滑，但这不能单独保证上述离散位置目标在电机端产生连续速度或平滑加速度。电机固件内部响应未知；规划点时间和关节位置间隔取决于具体轨迹，尚未核对本次执行的数据。抖动与该执行方式是否有关仍待验证。

历史核对显示，仓库可见的重构前真机 FJT 路径也按时逐点更新目标，未找到点间线性插值被重构删除的证据；重构改变了调度及多个到期点的处理，实际发送时序仍需对照。RViz 轻量预演及运动监控中的插值不等同于真机控制器插值。

### 待核查和讨论

- 记录同一次 MoveIt 轨迹的各轴位置、速度、加速度与时间，统计相邻点的时间和关节角间隔；根据需要计算末端路径。
- 对齐控制器实际发送目标及时间和新鲜电机反馈，检查目标跳变、跟踪误差与抖动之间是否有关联；同时评估通信、机械及电机控制因素。
- 评估时间插值或利用轨迹速度、加速度信息的可行性，包括起点、终点、稀疏点、跨周期跳点、取消保持、限位和碰撞路径；线性插值本身不能保证点处速度连续或加速度平滑。
- 评估共用执行层的分段多项式方案：三次 Hermite 在相邻段共享位置和速度时可保证参考位置、速度连续；五次 Hermite 在共享位置、速度、加速度时可保证参考加速度也连续，但不自动保证 jerk 限值。需定义速度或加速度缺失时的处理、网页键盘单点轨迹的起点和边界，并检查过冲、速度、加速度、jerk、限位与碰撞路径；不能简单把每个中间点的速度置零。周期离散发送及真实硬件响应仍需独立验证。
- 任何执行策略修改需单独审阅和离线验证，再在现场安全检查及明确授权后安排真机分项验收。
